# Precise routing with conservative uncertainty

TestLore separates repository inventory from the graph that native tests can reach. Native Jest/Vitest imports resolve from discovered test files and configuration roots, then follow local transitive imports using one framework configuration/server. Unrelated lint tools and benchmark scripts do not enter that resolver queue. Every source is still inventoried and analyzed; no ignore pattern conceals an unknown input.

Each graph warning has an explicit scope:

- `global`: incomplete collection/configuration, unsupported native context, registration hooks, missing declarations, invalid package/compiler metadata, or a warning in configuration or an imported global helper. Active changes run the full suite.
- `test-closure`: an unknown edge in a test or a source reachable by that test. Every consumer of that uncertain source runs on **every active change**, including changes outside its known dependency paths. A dynamic loader therefore cannot make a hidden consumer omittable. Known worker/thread, filesystem, process, virtual machine and network built-ins, direct fetch calls, and Worker/WebSocket/EventSource constructors add runtime uncertainty. Undeclared external package behavior and application-specific aliases remain limitations; observations do not certify their absence.
- `unreachable-source`: an unknown edge in source outside the known test/configuration closure. The warning remains visible but does not widen an independently mapped change. Changing that unmapped source still runs the full suite.

The plan exposes `uncertainty` counters/test lists and each retained test explains `uncertain-dependency-closure`. Existing baseline import edges remain included when a change removes an import. New, deleted, or unmapped inputs; package/lock/compiler changes; opaque global helpers; missing reports; stale observations; and unsupported project contexts retain their conservative fallback.

Native built-in Node/jsdom/happy-dom Vitest contexts resolve both client and SSR candidate edges. Arbitrary environments, Vitest project/workspace/browser contexts and `isolate: false` require full fallback until a complete native context graph is available. Configured setup files and their imported local helpers are global inputs, including setup names that do not contain “setup.” Node `--import`, `--require` and loader arguments are global configuration roots. Effective nonempty `NODE_OPTIONS` (with configured environment taking precedence over inheritance) is an unmodeled global runtime context and forces full selection; its hash binds capture/history provenance. This deliberately includes benign runtime options until their grammar and semantics are qualified. Vitest CLI isolation overrides also remain unsupported instead of bypassing the shared-runtime guard. Package boundaries do not hide a cross-package import: the transitive graph follows local resolved source across workspace directories; package/lock metadata changes remain global.

## Review-only mappings

`routingProposals(root)` returns bounded provenance-backed mapping candidates. It inspects reachable source for literal filesystem paths, `new URL('./asset', import.meta.url)` references and literal `path.join`/`path.resolve` calls rooted at `__dirname` or `import.meta.dirname`. Safe module-relative parent references can resolve within the project; escaped paths, symlinks, directories, missing paths, encoded URL references and computed expressions remain unresolved. A same-named function may be another API, and a literal reference may be unreachable: accepting a proposal adds an edge, never certifies a closed world or clears runtime uncertainty.

Reachable CSS/SCSS/Sass/Less files can suggest local `url(...)` resources and `@import` chains. Shared and cyclic style chains retain all observed static consumers, including per-test paths through other suggested style edges. These are literal text observations; comments, preprocessors and served URL bases require review. Remote, absolute, data and unresolved resources are recorded without making URL-to-source guesses. Browser requests and route mappings continue to use the separate provenance-backed browser observation API described in [browser mappings](browser-mappings.md).

For explicit root `package.json` workspaces (an array or a `packages` array), a static import of an unambiguous local package can propose a group containing that package's inventoried source, assets and metadata. The group excludes tests and ignored outputs; it does not establish native package binding, exports conditions, transitive services or build completeness. Unsupported/negated workspace patterns, duplicate package names and oversized groups remain warnings. pnpm-only declarations and framework-specific workspace metadata are not inferred by this inspector. Package/lock/runner metadata remains potentially global: proposals label those inputs `retain-global-configuration-fallback` and never relax the selector's existing configuration guard.

Direct `process.env` references ending in `URL`, `HOST`, `ENDPOINT`, `VERSION` or `REVISION` offer **service review suggestions only**. They contain variable names and consumer test paths, never current values or an automatically applicable service patch. A service endpoint or credential does not identify the serving revision. A maintainer must declare a trustworthy version signal and complete consuming scope before service freshness can contribute routing evidence. Executable service probes are rejected before proposal snapshots; native configured discovery/resolution can still execute project configuration as it already does during planning.

Candidates include a proposed `dependencies` patch, source/input hashes, consumer paths, configuration scope, explanations and limitations. Generated collections have a payload hash, producing module hash and full current provenance. Call `validateRoutingProposals(root, proposal)` before review or reuse; `qualifyRoutingMappings` also performs this check for generated collections before native full/subset evaluation. Configuration, source, service-version and producer-module drift reject reuse. Hashes detect changes to retained bytes; they are not signatures, proof of dependency completeness, or attestation of every imported/installed producer dependency. A caller can recompute a hash, so qualification still challenges actual native behavior independently. Historical manual unsealed proposals remain supported for compatibility and are explicitly labeled with unverified integrity/producer/completeness in the qualification report.

Generation emits at most 1,000 proposals, 1,000 inputs and 1,000 tests per proposal, 25,000 aggregate dependency edges and 512 KiB per inspected reference source. Oversized groups are withheld and marked truncated; truncated collections cannot acquire a successful qualification. These limits bound the suggested payload, not the upstream graph/snapshot's wall-clock execution. The command does not write configuration, enable completeness, or install an SDK. Full shadow runs and review remain necessary before maintainers apply added edges.

Browser/runtime observations and declarations may add edges; observation alone never removes an uncertain static consumer. Selection works at test-file granularity and does not imply deployment safety or time savings. Full/subset execution and end-to-end timings must qualify each real repository before enabling selective CI execution.
