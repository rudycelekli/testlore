# TestLore 0.2.0-alpha.1 candidate

**Status: source candidate, not a verified npm release.** A version change in Git is preparation. No publication, registry archive identity, provenance or fresh registry installation is claimed by this document.

The candidate brings the verification layer for coding agents and developers into one first-use path: shadow setup, actionable native outcomes, bounded source repair, complementary adapter policy and workspace-aware native case identities. Each feature retains its own qualification scope. A packaged feature list does not establish general application compatibility or superiority.

## Use current source now

From a project with its native test dependencies installed:

```sh
npm exec --yes --package=github:rudycelekli/testlore#main -- testlore setup --verify
```

Human output leads with the advisory verdict, failures, proposed versus executed files, fallback causes, native scope and next action. Add `--json` for agents or scripts. These are candidate source features, not currently verified npm candidate commands.

This is the same recommended source command as the [README](../../README.md) and [adoption guide](../adoption.md). `#main` moves: replace it with a reviewed full Git SHA for reproducibility. The adoption guide records a previously reviewed immutable fallback and explicitly limits that fallback to its earlier source. Setup attempts a full native shadow run and returns prerequisites or observed outcomes; it preserves native failure exits. Inspect and commit generated configuration and workflows before activating ongoing operation.

Temporary execution does not install a persistent project dependency. Install the same reviewed Git revision locally before later `npx --no-install` commands. No optional adapter download or provider call is performed by setup. Agent generation and repair require separately configured workers and independent requirements.

## What publication must prove

1. Review and merge one exact source revision; require source qualification, native/browser controls and packed-install gates to pass on that revision.
2. Dispatch `Alpha release candidate` on `main` with `source_sha` equal to that reviewed full SHA and `publish: false`. The workflow independently qualifies source, measured/native selector controls, browser controls, then seals and checks one exact production archive. Preserve the archive SHA-256, npm integrity, source SHA, raw receipts and failures.
3. Independently inspect the exact archive and installed CLI evidence. A passing source suite does not qualify different archive bytes.
4. Verify npm's trusted-publisher mapping for repository `rudycelekli/testlore`, workflow `alpha-release.yml` and the expected protected `npm-alpha` environment. The mapping is an external account configuration, not something inferred from the workflow's `id-token: write` permission.
5. Publish only through the protected workflow from the still-current reviewed `main` SHA using trusted OIDC. The workflow qualifies a newly sealed exact archive before its own publish phase; do not substitute an archive from another run or assume a prior run's digest remains its authorization. Publish under the `alpha` channel, preserve `latest` deliberately and do not overwrite the immutable `0.1.0` release or its historical evidence.
6. Require registry metadata and downloaded archive bytes to match that run's sealed receipt, then exercise a fresh production registry installation and the exact documented one-command setup. The workflow now runs `scripts/registry-setup-proof.js` against the exact version, with a fresh isolated cache, empty npm profiles and no inherited provider credentials. Its controlled Node projects preserve two named passing outcomes, explicitly disabled adapters, and a real native failure with exit 1. Installed manifest and retained CLI bytes must match the independently qualified archive identities. Preserve raw process logs, configuration, registry bindings and actionable first-result fields; this checks a bounded adoption path, not broad application compatibility.
7. Only after those gates pass, update recommended installation to the exact `testlore@0.2.0-alpha.1` version and record permanent release receipts. A moving tag is not a substitute for an immutable version/digest.

Local preparation tools are `scripts/release-candidate.js`, `scripts/packed-proof.js`, `scripts/registry-proof.js`, `scripts/registry-setup-proof.js` and `scripts/npm-readiness.js`. Read their arguments and checks before using them. Archive sealing requires a clean committed checkout and a new output directory. Neither the sealing script nor this document performs publication or changes account protection. The registry setup proof refuses an unavailable version; evaluator controls do not qualify registry execution. Its raw replay verifies captured consistency, while independent receipt and producer bindings establish lineage separately.

## Current launch blockers

The current readiness inspection found no usable interactive npm identity. GitHub's protected `npm-alpha` environment is present. The npm trusted-publisher mapping is **unknown**, not certified. No credentials belong in chat, artifacts or reports. The workflow requires token-free GitHub OIDC; an unrelated local token does not qualify the publisher mapping.

Exact candidate source/archive gates and registry setup verification remain required. Passing earlier `0.1.0` registry checks only qualifies its immutable archive. [Historical release evidence](../npm-release-0.1.0.md) remains unchanged.

## Evidence limits users should see

- Real application routing still has conservative full-suite fallbacks. The pinned e2e qualification preserved 2,495 case identities and all six retained regression exposures, but omitted zero files and took longer than native selection. Workspace/context parity is useful evidence; it is not a performance win.
- Node source repair is a bounded first profile. The recorded native Codex repair used explicitly adapted Node assertions, not a complete untouched upstream suite. Broader agent repair reliability and live PR publication remain separate gates.
- Learning remains advisory; current comparisons do not demonstrate repeatable improvement.
- No maintainer participation, accepted improvements, repeat adoption or best-in-class result is established merely by preparing or publishing an alpha.

A pilot should record installation success, time to first actionable result, independent defects caught, unchanged regression preservation, proposed/accepted improvements, total runtime/cost and human oversight. Retain negative outcomes and share only explicitly reviewed aggregate or sanitized public evidence. [Pilot scope](../adoption.md#pilot-participation).
