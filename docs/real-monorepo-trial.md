# Real monorepo trial: make uncertainty actionable

The pinned [e2e campaign](contributed-e2e.md) exercises the original monorepo installation and build, then one complete unit project. Full fallbacks and native timing losses remain recorded. A fresh run is a measurement, not automatic permission to omit tests.

Inspecting its actual retained TestLore plan exposed a diagnostic failure: `diagnoseFallbackSelection` rejected `../../tsconfig.base.json`, even though the graph deliberately records that inherited configuration as a global uncertainty warning. The diagnostic now accepts this bounded label only for an exact `external-resolution-config` global warning with explicitly empty consumers. It is display-only: no external file is read, no dependency is created, and full fallback remains required. Outside-root changes, test identities, dependency paths and other warning kinds remain rejected.

Each new campaign trial retains a `change-<n>-trial-<n>-fallback-diagnostic.json` alongside the actual full/native/TestLore outputs. Its selection digest binds the captured plan, and its actions distinguish inherited configuration from registration side effects. The controller loads diagnostics from the sealed installed candidate, records its producer hash, and rejects producer drift. These offline explanations do not verify current source freshness or prove omission safety. [Implementation](../src/fallback-diagnostics.js) · [Boundary controls](../test/fallback-diagnostics.test.js).

The observed routing blockers are one inherited TypeScript configuration outside package inventory, 14 globally classified registration calls, and scoped runtime/dynamic dependency uncertainty. The runtime-registration scanner matches domain `.register` calls as well as module hooks; suppressing that warning by method name would not establish dependency completeness. A workspace-root profile must also qualify native root/configuration parity before it can authorize narrower execution.

Case preservation has a separate blocker. The original JSON has 2,495 cases and 2,494 unique file/title identities. Two rows of one `it.each` call have distinct inputs but the same title and source location. [Vitest's native IDs](https://vitest.dev/api/advanced/test-case) depend on project, module and registration order; they do not identify parameter values. The frozen October 9 captures remain identity-incomplete. The [October 11 exact-source observer](contributed-e2e.md#native-case-qualification-2026-10-11) now independently qualifies all 2,495 native case identities in the original package profile, including actual distinct inputs for those duplicate rows. It does not retroactively qualify old captures, clear dependency uncertainty, justify omissions or establish a speed advantage.

Success for the next routing experiment requires genuine original installation, unchanged protected tests/configuration, independently demonstrated failures, complete full/subset outcomes, explanations for each omission, and complete runtimes against native selection. Missing evidence keeps conservative fallback. This diagnostic correction improves real campaign usability; it establishes no speed or learning gain.

The workspace inventory profile must also preserve the original package working directory. An actual native monorepo-cwd baseline failed three path-sensitive original cases; absolute root/config arguments alone did not preserve behavior. The explicit `nativeCwd` admission binds a canonical in-inventory package directory and keeps native execution there. See [ADR 006](adr/006-workspace-context-and-native-registration-evidence.md) for rejection and qualification requirements.
